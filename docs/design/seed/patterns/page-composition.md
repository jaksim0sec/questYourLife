# 페이지를 구성하는 방법

> **대상:** AI 코딩 에이전트와 사람 디자이너. 사용자가 끼워 넣는 블록 에디터가 아니다. 페이지별 템플릿을 표준 컴포넌트로 등록하는 절차도 아니다. 기존 [정보 위계](content-hierarchy.md)의 목적·객체 판단을 **화면 전체의 공간 설계와 연결**하는 지침이다.

## 1. 한 페이지를 만드는 데 필요한 결정

**페이지 목적 → 담을 정보와 행동 → 의미상 섹션 → 배치의 공간 관계 → 기존 컴포넌트·표면·아트 → 실제 결과.**

이 순서는 문서 작성 순서와 다르다. SEED 라이브러리 자체는 Foundation/Component에서 정립되지만, 페이지 제작은 이미 있는 부품을 먼저 늘어놓고 콘텐츠를 끼워 맞추면 안 된다.

| 결정을 먼저 해야 하는 것 | 한 줄로 답할 질문 | 책임 |
|---|---|---|
| 페이지 목적 | 누가 지금 무엇을 확인하거나 하려 하는가 | 제품/화면 |
| 범위 | 이 화면에서 꼭 필요한 것과 상세/다른 화면으로 보내야 하는 것은 무엇인가 | 제품/화면 |
| 콘텐츠·행동 | 조회 데이터와 변동 수치, 클릭 결과, 서로 중복되는 정보는 무엇인가 | 제품/화면 |
| 섹션 | 함께 읽어야 하는 정보 그룹과 우선순위는 무엇인가 | 페이지 |
| 공간 배치 | 비교/탐색/순서/동시 노출 관계에 맞는 배열은 무엇인가 | [공간 배치](layout-composition.md) |
| 표현·행동 | 어느 기존 컴포넌트 슬롯·Surface·아트 레벨이 맞는가 | 기존 SEED |
| 결과 판정 | 첫 시선·정보 완결성·클릭 기대가 목적과 맞는가 | 페이지·사용 경험 |

이 기준은 별도의 7개 문서, 관리 테이블이나 신규 프레임워크를 요구하지 않는다.

## 2. 섹션을 나누는 판단

섹션은 **정보상 독립된 목적**이 있을 때 분리한다. 기능명·테이블명·버튼명마다 섹션을 만들지 않는다.

**같은 섹션으로 묶는 쪽:** 함께 읽어야 의미가 생김 / 하나의 주요 목적지나 행동을 공유함 / 제목 없이도 한 덩어리로 이해됨.

**나누는 쪽:** 이벤트 홍보와 현재 공동 진행처럼 목적이 다름 / 한 정보가 다른 정보를 밀어냄 / 행동 목적지가 달라 한 카드에 여러 주행동이 경쟁함 / 모음의 선택·필터 범위가 다름.

**다른 페이지로 보내는 쪽:** 당장 결정에 불필요한 세부 이력·긴 조건·전체 목록 / 홈의 역할을 침범하는 상세 탐색 / 중복된 같은 목적지 링크.

**무엇이 아니다:** 카드가 곧 섹션이 아니고, Section Header는 필수가 아니다. Plain 공간도 유효한 섹션이다. 서로 다른 두 그룹을 한 Surface 안에 넣을 수 있지만, 독립 책임인지 먼저 판정해야 한다.

## 3. 페이지 골격과 공간 배치 적용

1. **Shell:** Root/Detail/Utility 등은 [Page Shell](../shells/page-shells.md)과 [Top Navigation](../../TOP_NAVIGATION.md)에서 선택. 헤더 슬롯·스크롤·Bottom Navigation·고정 CTA·safe-area를 다시 정의하지 않음.
2. **섹션 지도:** 첫 화면에서 읽을 정보와 보조 정보를 목적 순서대로 놓는다. 실제 화면 전체에서 큰 면적을 가질 이유를 설명한다.
3. **섹션 내부:** [공간 배치](layout-composition.md)의 세로·가로·격자·겹침 중 정보 관계에 맞는 구조를 배치. 필요하면 안쪽에서 다른 구조를 중첩.
4. **실제 구성:** 기존 [List](../components/list-item.md), [Image Frame](../components/image-frame.md), [Action](../components/action-button.md), [Status](../components/badge-progress.md), [Text](../components/text-hierarchy.md), [Surface](../components/surface-media.md) 등 정본의 슬롯·Variant를 우선 사용.
5. **표현 수준:** 이미지는 이미지로, 실제 수치·텍스트·선택·행동은 UI로 관리. [Reward Art](../assets/reward-art.md)의 A1/A2/A3 기준을 보존하고 기존 원본 에셋을 임시 그래픽으로 대체하지 않음.

**구조적 예외:** Surface를 선택했다고 해서 무조건 그 안에 Container를 추가하지 않는다. 필요한 레이아웃만 존재하고 Surface=Plain일 수 있다.

## 4. 모델이 실제로 고르는 방법

레이아웃 유형을 정답표로 외우지 말고, **같은 콘텐츠를 다른 목적에 배치한 반례**를 함께 생각한다.

| 페이지가 표현해야 하는 관계 | 적합한 첫 후보 | 달라지는 조건 |
|---|---|---|
| 순위·설정·일일 행동을 **텍스트와 숫자 기준으로 비교** | 세로 배치 + 기존 List | 이미지 작품의 발견/흥미가 주연이면 Rail 가능 |
| 이미지 작품·상품을 **여러 개 동시에 비교** | Grid + 공통 Image Frame | 한 장씩 순차 탐색하려면 Rail |
| 썸네일과 제목·정보를 함께 스캔 | 가로 Weighted + 기존 Media/List | 제목이 길거나 320 폭이면 세로 전환 |
| 다른 맥락의 정보 그룹을 한 페이지에 배치 | 섹션별 적합한 Layout + 전체 세로 흐름 | 섹션 목적 자체가 중복이면 그룹을 줄이거나 다른 화면으로 이동 |
| 한정 보상 장면 + 짧은 메시지 | 안전영역이 있는 겹침 배치/Media | 실제 진행 수치나 반복 목록까지 넣어야 하면 별도 섹션으로 분리 |
| 메시지 안의 AI 계획 제안 | 기존 메시지 흐름 안의 정보 객체·행동 조합 | 제안 콘텐츠가 독립 화면을 요구하지 않으면 새 Page Type을 만들지 않음 |

## 5. 페이지 자유도와 기존 규격의 경계

| 페이지에 맡기는 결정 | SEED가 강제하는 계약 |
|---|---|
| 섹션의 존재·순서·중요도 | 목적 중복을 방지하고 사용자의 주요 과업이 드러나야 함 |
| 가로/세로/격자/겹침 선택 | 배치의 Gap·정렬·반응형·overflow 계약과 기존 F-GEOMETRY |
| 이미지 비중·원본 종류·콘텐츠 개수 | Image Frame의 contain/cover/ratio, Reward Art, 이미지 안전영역 |
| 표시할 상태·가격·다음 행동 | 해당 정보 객체와 C-TEXT/C-CREDIT/C-STATUS/C-ACTION 슬롯·상태 |
| 텍스트/표면의 강조 강도 | 승인된 Text/Surface/CTA role·색·반경·타깃 |
| 구체적 경로와 탐색 책임 | 확정된 NAV-TOP/S-PAGE와 실제 사용자 플로우 |

배치 재량이 있다는 이유로 CSS에서 기존 버튼 높이·아이콘 모양·텍스트 역할·색을 페이지별로 덮지 않는다. 반대로 표면/레이아웃 규격을 따른다고 모든 페이지의 섹션 순서를 똑같이 하지 않는다.

## 6. 정보 객체의 경계: Layout이 대신하면 안 되는 것

**아이템:** 같은 모자라도 상점의 가격, 보관함의 소유·장착, 수령 결과의 획득 사실이 달라진다. Grid/Rail은 항목의 위치만 관리하고 정보 슬롯과 상태를 버리지 못하게 한다. C-IMAGE의 Overlay 위치는 이 Layout이 이중 정의하지 않는다.

**공동 보상:** '홍보/참여 유도'와 '공동 진행 확인'과 '실제 지급 결과'는 같은 데이터를 공유해도 섹션 목적이 다름. 하나의 Hero에 홍보·Progress·보상 구성·CTA를 모두 얹지 않는다. 반대로 반드시 세 카드로 나눈다는 규칙도 아니다.

**액션:** 이동용 저강도 링크와 실제 수령/확정은 다른 상태와 책임. 이미지에 '받기' 버튼 그림이 있더라도 실제 수령 UI를 대체하지 못한다. 지급 연동이 없으면 완료·수령을 암시하지 않는다.

## 7. 최소한의 설계 기록

새 페이지 작업 시 기존 작업 계획/PR 설명에 아래 여섯 항목만 기록하면 된다. 단순 컴포넌트 수정에 매번 반복하지 않는다.

1. **목적:** 누구의 무엇을 해결하는가. 인접 페이지 책임은 무엇인가.
2. **섹션 지도:** 필수→보조 순서와 분리·결합 이유, 중복 정보 제거.
3. **배치 선택:** 섹션별 선택한 배치/Variant, 선택 이유, 배제한 후보 하나.
4. **기존 SEED 재사용:** Shell/Component/Surface/Art 정본과 새로운 예외 여부.
5. **첫 시선과 행동:** 가장 먼저 읽을 정보, 주행동 하나, 보조 행동의 위치와 강조 이유.
6. **근거와 한계:** 시안/실제 데이터/가정 구분, 실제 렌더·동작 결과 및 아직 검증하지 않은 것.

**예시 기록 (화면 확정안 아님):** '클랜 멤버 기여도는 수치를 비교하므로 세로 배치 + List. 동등한 수치 기준선과 약한 Divider를 택함. 웹툰의 이미지 중심 인기 작품 목록은 순차 발견이므로 Rail + Image Frame. 둘 다 랭킹이지만 동일 Layout 강제하지 않음.'

## 8. 실패를 판단하고 돌아갈 위치

| 증상 | 먼저 확인할 판단 | 수정 대상 |
|---|---|---|
| 이벤트 상자가 구성원 활동을 밀어냄 | 페이지 주연·섹션 책임·면적 배분 | Page/섹션 지도; 높이만 임시 축소 금지 |
| 이미지+작은 이름뿐이라 아이템을 해석 못함 | 정보 슬롯·상태·가격의 맥락 | 객체 조합과 C-IMAGE/C-CREDIT; Grid 자체 수정 아님 |
| 모든 화면이 같은 카드 목록처럼 보임 | 데이터의 비교/탐색/표현 목적과 Surface 과용 | Layout 선택 + C-SURFACE |
| 같은 버튼이 페이지마다 모양·크기가 바뀜 | 기존 컴포넌트 Variant 재사용 여부 | C-ACTION·공통 스타일, Layout 별도 추가 금지 |
| 배지 위치가 화면마다 어긋남 | Image Frame/컴포넌트에 이미 Anchor가 있는가 | 기존 Component 슬롯, 별도 Layer 생성 금지 |
| 상세 화면 버튼이 하단바·키보드에 가림 | Shell의 fixed 영역·inset 소유권 | S-PAGE; 지역 padding 누적 금지 |
| 브라우저 렌더는 되지만 디자인 목적이 전달 안 됨 | 첫 시선·정보 위계·원본 아트·행동 관계 | 해당 Page/Pattern 선택. 테스트 수만 늘리지 않음 |

## 9. 검토의 경계

- 이번 문서화는 **범용 레이아웃과 페이지 선택 규칙의 설계안**이다. 새 UI 코드·페이지 시연·이동 동작·네이티브·접근성 실증은 다루지 않는다.
- [VALIDATION](../VALIDATION.md)의 실행/규격/객체·조합/페이지 목적/행동·회귀 다섯 축은 유지한다. 문서 간 경로가 맞다고 디자인 품질이 입증된 것은 아니다.
- 최종 홈/클랜/마이/상점의 콘텐츠 순서·면적 및 아트 강도는 실제 화면에서 판단한다. 해당 미결은 [OPEN](../../../OPEN.md)에 남아 있다.
