# 페이지를 구성하는 방법

> **대상:** AI 코딩 에이전트와 사람 디자이너. 사용자가 끼워 넣는 블록 에디터가 아니다. 페이지별 템플릿을 표준 컴포넌트로 등록하는 절차도 아니다. 기존 [정보 위계](content-hierarchy.md)의 목적·객체 판단을 **화면 전체의 공간 설계와 연결**하는 지침이다.

## 1. 한 페이지를 만드는 데 필요한 결정

**페이지 목적 → 담을 정보와 행동 → 의미상 섹션 → 배치의 공간 관계 → 기존 컴포넌트·표면·아트 → 실제 결과.**

이 순서는 문서 작성 순서와 다르다. SEED 라이브러리 자체는 Foundation/Component에서 정립되지만, 페이지 제작은 이미 있는 부품을 먼저 늘어놓고 콘텐츠를 끼워 맞추면 안 된다.

| 결정을 먼저 해야 하는 것 | 한 줄로 답할 질문 | 책임 |
|---|---|---|
| 페이지 목적 | 누가 지금 무엇을 확인하거나 하려 하는가 | 제품/화면 |
| 범위 | 이 화면에서 꼭 필요한 것과 상세/다른 화면으로 보내야 하는 것은 무엇인가 | 제품/화면 |
| 콘텐츠·행동 | 조회 데이터와 변동 수치, 클릭 결과, 서로 중복되는 정보는 무엇인가 | 제품/화면 |
| 섹션 | 함께 읽어야 하는 정보 그룹과 우선순위는 무엇인가 | 페이지 |
| 공간 배치 | 비교/탐색/순서/동시 노출 관계에 맞는 배열은 무엇인가 | [공간 배치](layout-composition.md) |
| 표현·행동 | 어느 기존 컴포넌트 슬롯·Surface·아트 레벨이 맞는가 | 기존 SEED |
| 결과 판정 | 첫 시선·정보 완결성·클릭 기대가 목적과 맞는가 | 페이지·사용 경험 |

### 콘텐츠 구성 경향 (S03 · 새로운 Page Type 아님)

페이지에서 가장 먼저 결정할 것은 **사람이 다양한 콘텐츠를 발견하려는가, 일정한 자료를 열람·비교하려는가, 둘 다 필요한가**이다. 아래 셋은 고정된 페이지 템플릿이나 추가 런타임 유형이 아닌 **구성 선택의 경향**이다. 각 섹션의 목적이 다르면 한 페이지에서 서로 섞어 쓴다. `Global / Global Inner / Non-Global / Bottom Sheet`는 계속 [S-PAGE](../shells/page-shells.md)의 내비게이션 가시성 계약이며, 어느 경향도 특정 Page Type을 강제하거나 배제하지 않는다.

| 경향 | 정보의 핵심 관계 | 기존 SEED로 구성하는 첫 후보 | 강제하지 않을 것 |
|---|---|---|---|
| **발견·탐색 중심** | 실시간 정보·소식·트렌드·추천·이벤트 등 서로 다른 콘텐츠를 발견하고 각 흐름에 진입 | 주연이 이미지인지 제목인지에 따라 Media/Identity + Rail·Grid, 세로 피드·List를 섹션별로 선택. 한 화면에 가로와 세로 탐색이 공존할 수 있음 | 모든 유형을 한 화면에 다 넣기, 모든 섹션을 배너·카드로 강조, Rail 고정 |
| **정보 열람 중심** | 랭킹·알림·기록·정형 목록을 같은 기준선으로 분류·읽기·비교·확인 | 반복 List/세로 배치, 동일한 숫자·상태 슬롯. 범주가 실제로 있을 때만 Tabs/Segmented 등의 선택 사용 | 탭·알약형 선택 필수화, 보통 Global에서 덜 쓰인다는 경향을 금지 규칙으로 오해 |
| **혼합 구성** | 인사이트·추천처럼 발견할 정보와 정형 목록·기록처럼 차례로 읽을 정보가 함께 필요 | 목적이 다른 섹션에 각각 적합한 Rail/Grid/Rows와 Plain/Media 등 기존 표현 선택 | 발견 섹션 위·열람 섹션 아래의 고정 순서, 50:50 면적, 항상 혼합하기 |

**선택 순서:** ① 페이지에서 해결할 과업과 필수 콘텐츠를 정한다 → ② 각 정보 묶음이 발견/열람 중 어떤 읽기 관계인지 판단한다 → ③ 두 목적이 함께 필요할 때만 혼합 구성한다 → ④ [P-LAYOUT](layout-composition.md)의 기존 세로·가로·격자·겹침, [P-HIERARCHY](content-hierarchy.md)의 정보 위계, [C-SURFACE](../components/surface-media.md)의 표면을 **섹션마다 독립적으로** 고른다. 콘텐츠가 과밀하거나 목적지가 중복되면 상세 화면으로 넘기거나 그룹을 줄이지, '발견형'을 핑계로 모든 것을 한 화면에 쌓지 않는다.

**같은 Page Type이어도 구성은 다르다:** 현행 웹 미리보기의 `#clan-discover`(클랜 발견)와 `#clan-record`(기록 열람)는 둘 다 `global-inner`로 라우팅되지만, 전자는 미디어 중심 발견, 후자는 수치·반복 행 비교를 우선할 수 있다. 이는 **S-PAGE의 Standard 헤더와 Global Inner 하단바 표시 계약을 바꾸지 않고 내부 구성만 달리해야 한다는 예시**다. 다만 레거시 `clan.css`에는 `global-inner`의 `#nav`를 숨기는 선택자가 남아 있어 현행 미리보기가 이 계약을 실제로 충족한다는 뜻은 아니다(기준선 U00에서 후속 회귀 후보로 분리). 두 화면의 픽셀 품질 승인이나 콘텐츠 배치 강제도 아니다. 하나의 Global 화면에서도 발견과 정보 열람을 섞거나 열람만 택할 수 있다.

**반례:** '랭킹'이라는 이름만으로 정형 세로 목록을 강제하지 않는다. 수치 비교가 목적이면 List, 콘텐츠를 찾아보는 목적이면 Rail이 가능하다. 발견·열람·혼합이라는 이름으로 CSS 클래스, 새 Section/Surface Variant, Tab 필수 슬롯 또는 새 페이지 분류를 만들지 않는다.

이 기준은 별도의 7개 문서, 관리 테이블이나 신규 프레임워크를 요구하지 않는다.

## 2. 섹션을 나누는 판단

섹션은 **정보상 독립된 목적**이 있을 때 분리한다. 기능명·테이블명·버튼명마다 섹션을 만들지 않는다.

**같은 섹션으로 묶는 쪽:** 함께 읽어야 의미가 생김 / 하나의 주요 목적지나 행동을 공유함 / 제목 없이도 한 덩어리로 이해됨.

**나누는 쪽:** 이벤트 홍보와 현재 공동 진행처럼 목적이 다름 / 한 정보가 다른 정보를 밀어냄 / 행동 목적지가 달라 한 카드에 여러 주행동이 경쟁함 / 모음의 선택·필터 범위가 다름.

**다른 페이지로 보내는 쪽:** 당장 결정에 불필요한 세부 이력·긴 조건·전체 목록 / 홈의 역할을 침범하는 상세 탐색 / 중복된 같은 목적지 링크.

**무엇이 아니다:** 카드가 곧 섹션이 아니고, Section Header는 필수가 아니다. Plain 공간도 유효한 섹션이다. 서로 다른 두 그룹을 한 Surface 안에 넣을 수 있지만, 독립 책임인지 먼저 판정해야 한다.

### S04 · 섹션 외형: Borderless와 Container (새 Surface 종류 아님)

| 표현 | 먼저 판단할 이유 | 기존 SEED 조합 | 피해야 할 오해 |
|---|---|---|---|
| **Borderless · 일반 섹션** | 제목·내용·인접 섹션 간 간격만으로 관계를 읽을 수 있음 | 기존 **Plain** Surface + F-GEOMETRY의 섹션/그룹 간격 + 필요할 때 Divider | 손그림에 그려진 섹션 외곽선을 실제 CSS `border`로 만들거나, 모든 섹션마다 카드 배경을 넣기 |
| **Container · 독립 콘텐츠 묶음** | 한 목적의 여러 정보를 함께 읽게 하거나 다른 흐름과 구별해 주목시킬 필요가 있음 | 기존 C-SURFACE의 **Solid / Outlined / Subtle** 등 필요한 강도의 표면 선택. 독립 Media/Reward는 각 정본의 제한을 따름 | 새 `Container` 컴포넌트·제11의 Surface 신설, 모든 Section을 박스형으로 고정하기 |

**섹션 조합:** [타이틀? / 부제? / 제목 우측 보조 Action?] + **콘텐츠** + [관련 후행 Action?]. 물음표 슬롯은 모두 선택적이며 없는 슬롯 때문에 빈 면적을 예약하지 않는다. 섹션 제목은 없을 수도 있고, 있더라도 오른쪽 액션은 필수가 아니다.

**제목 옆 보조 Action의 기본 표현 (S04):** `전체보기` / `더보기` / `자세히`처럼 섹션 내용으로 이동하는 경우 **무테·무배경의 짧은 텍스트 링크**를 우선한다. 필요하면 작은 Chevron을 곁들이되, 제목보다 낮은 강조를 유지한다. 이것은 **제목 옆에 C-ACTION의 테두리 있는 Outline/채워진 Solid/Pill Button을 배치하라는 뜻이 아니다.** 이동은 실제 링크로, 페이지 상태를 바꾸는 동작은 기존 C-ACTION의 `textAction` / `ghost`처럼 표면 없는 보조 액션으로 처리한다. 별도 실행·확정·수령 CTA가 필요하면 제목 옆 보조 링크로 오인시키지 말고 본문 또는 Footer에서 행동 위계를 판단한다. 제목 옆에 무테 텍스트 Action이 있다는 이유로 새 Component·Variant·임의 CSS를 만들지 않는다. 투명한 터치 영역·포커스 표시는 기존 접근성 계약대로 보장한다.

```text
이번 주 활동                          전체보기 ›
활동 목록 ...
```

제목이 길거나 320 폭·글자 200%에서 오른쪽 보조 액션과 충돌하면 **행 높이를 늘리거나 위치를 재배치**한다. 제목·액션을 잘라내거나 글자만 축소해서 해결하지 않는다.

**도식의 읽는 법:** 손그림의 점선·사각형·둥근 모서리는 **섹션의 공간 범위와 정보의 소속 관계**를 설명한다. CSS 테두리·배경·그림자·radius 지시가 아니다. 일반 Container를 이벤트 컨테이너로 자동 해석하지 않는다. 이벤트의 단일 이미지/동적 UI 선택은 별도 S09(U05)에서 판단한다.

### S04 · 섹션 타이틀의 표현 예시 (기존 C-TEXT/F-TYPE만 사용)

| 원본 이름 | 원본 예시 | 의도와 기존 Typography 활용 |
|---|---|---|
| **1줄형** | `어떤 취향을 갖고 있나요?` | 짧은 문장·일반 제목의 한 줄 표현. **질문형은 예시일 뿐 필수가 아님**. 목적에 맞는 기존 Section/Body 또는 필요한 타이틀 역할을 사용 |
| **큰형** | `제목 #1` / `본문 내용이 하단에 들어감` | 주제 제목과 아래 보조 본문의 크기·간격 차이. 실제로 주연인 경우 기존 Display/Hero, 그렇지 않으면 Section/Body 등으로 위계를 조정 |
| **트렌디형** | `FRESH FINDS` / `새로 발견하기` | 영문 소제목(레이블)과 한글 제목을 서로 다른 위계로 읽는 표현. 기존 Caption/Support + Section/Title을 맥락에 맞게 선택하며 남용하지 않음 |

세 표현은 화면별 **선택 가능한 제목 구성 사례**다. 3개 모두 사용하거나 질문·영어 소제목을 강제하지 않는다. 새로운 Text role·폰트 토큰·제목 Variant를 추가하지 않는다. HTML heading 순서는 문서 의미대로 정하고 시각 크기를 HTML 태그에 종속하지 않는다. Root/Standard 헤더의 D-015 승인 폰트·여백은 Section 제목 스타일을 이유로 변경하지 않는다.


## 3. 페이지 골격과 공간 배치 적용

1. **Shell:** Root/Detail/Utility 등은 [Page Shell](../shells/page-shells.md)과 [Top Navigation](../../TOP_NAVIGATION.md)에서 선택. 헤더 슬롯·스크롤·Bottom Navigation·고정 CTA·safe-area를 다시 정의하지 않음.
2. **섹션 지도:** 첫 화면에서 읽을 정보와 보조 정보를 목적 순서대로 놓는다. 실제 화면 전체에서 큰 면적을 가질 이유를 설명한다.
3. **섹션 내부:** [공간 배치](layout-composition.md)의 세로·가로·격자·겹침 중 정보 관계에 맞는 구조를 배치. 필요하면 안쪽에서 다른 구조를 중첩.
4. **실제 구성:** 기존 [List](../components/list-item.md), [Image Frame](../components/image-frame.md), [Action](../components/action-button.md), [Status](../components/badge-progress.md), [Text](../components/text-hierarchy.md), [Surface](../components/surface-media.md) 등 정본의 슬롯·Variant를 우선 사용.
5. **표현 수준:** 이미지는 이미지로, 실제 수치·텍스트·선택·행동은 UI로 관리. [Reward Art](../assets/reward-art.md)의 A1/A2/A3 기준을 보존하고 기존 원본 에셋을 임시 그래픽으로 대체하지 않음.

**구조적 예외:** Surface를 선택했다고 해서 무조건 그 안에 Container를 추가하지 않는다. 필요한 레이아웃만 존재하고 Surface=Plain일 수 있다.

## 4. 모델이 실제로 고르는 방법

레이아웃 유형을 정답표로 외우지 말고, **같은 콘텐츠를 다른 목적에 배치한 반례**를 함께 생각한다.

| 페이지가 표현해야 하는 관계 | 적합한 첫 후보 | 달라지는 조건 |
|---|---|---|
| 순위·설정·일일 행동을 **텍스트와 숫자 기준으로 비교** | 세로 배치 + 기존 List | 이미지 작품의 발견/흥미가 주연이면 Rail 가능 |
| 이미지 작품·상품을 **여러 개 동시에 비교** | Grid + 공통 Image Frame | 한 장씩 순차 탐색하려면 Rail |
| 썸네일과 제목·정보를 함께 스캔 | 가로 Weighted + 기존 Media/List | 제목이 길거나 320 폭이면 세로 전환 |
| 다른 맥락의 정보 그룹을 한 페이지에 배치 | 섹션별 적합한 Layout + 전체 세로 흐름 | 섹션 목적 자체가 중복이면 그룹을 줄이거나 다른 화면으로 이동 |
| 한정 보상 장면 + 짧은 메시지 | 안전영역이 있는 겹침 배치/Media | 실제 진행 수치나 반복 목록까지 넣어야 하면 별도 섹션으로 분리 |
| 메시지 안의 AI 계획 제안 | 기존 메시지 흐름 안의 정보 객체·행동 조합 | 제안 콘텐츠가 독립 화면을 요구하지 않으면 새 Page Type을 만들지 않음 |

## 5. 페이지 자유도와 기존 규격의 경계

| 페이지에 맡기는 결정 | SEED가 강제하는 계약 |
|---|---|
| 섹션의 존재·순서·중요도 | 목적 중복을 방지하고 사용자의 주요 과업이 드러나야 함 |
| 가로/세로/격자/겹침 선택 | 배치의 Gap·정렬·반응형·overflow 계약과 기존 F-GEOMETRY |
| 이미지 비중·원본 종류·콘텐츠 개수 | Image Frame의 contain/cover/ratio, Reward Art, 이미지 안전영역 |
| 표시할 상태·가격·다음 행동 | 해당 정보 객체와 C-TEXT/C-CREDIT/C-STATUS/C-ACTION 슬롯·상태 |
| 텍스트/표면의 강조 강도 | 승인된 Text/Surface/CTA role·색·반경·타깃 |
| 구체적 경로와 탐색 책임 | 확정된 NAV-TOP/S-PAGE와 실제 사용자 플로우 |

배치 재량이 있다는 이유로 CSS에서 기존 버튼 높이·아이콘 모양·텍스트 역할·색을 페이지별로 덮지 않는다. 반대로 표면/레이아웃 규격을 따른다고 모든 페이지의 섹션 순서를 똑같이 하지 않는다.

## 6. 정보 객체의 경계: Layout이 대신하면 안 되는 것

**아이템:** 같은 모자라도 상점의 가격, 보관함의 소유·장착, 수령 결과의 획득 사실이 달라진다. Grid/Rail은 항목의 위치만 관리하고 정보 슬롯과 상태를 버리지 못하게 한다. C-IMAGE의 Overlay 위치는 이 Layout이 이중 정의하지 않는다.

**공동 보상:** '홍보/참여 유도'와 '공동 진행 확인'과 '실제 지급 결과'는 같은 데이터를 공유해도 섹션 목적이 다름. 하나의 Hero에 홍보·Progress·보상 구성·CTA를 모두 얹지 않는다. 반대로 반드시 세 카드로 나눈다는 규칙도 아니다.

**액션:** 이동용 저강도 링크와 실제 수령/확정은 다른 상태와 책임. 이미지에 '받기' 버튼 그림이 있더라도 실제 수령 UI를 대체하지 못한다. 지급 연동이 없으면 완료·수령을 암시하지 않는다.

## 7. 최소한의 설계 기록

새 페이지 작업 시 기존 작업 계획/PR 설명에 아래 여섯 항목만 기록하면 된다. 단순 컴포넌트 수정에 매번 반복하지 않는다.

1. **목적:** 누구의 무엇을 해결하는가. 인접 페이지 책임은 무엇인가.
2. **섹션 지도:** 필수→보조 순서와 분리·결합 이유, 중복 정보 제거.
3. **배치 선택:** 섹션별 선택한 배치/Variant, 선택 이유, 배제한 후보 하나.
4. **기존 SEED 재사용:** Shell/Component/Surface/Art 정본 ID, **실제 공유 CSS/컴포넌트 클래스, 해당 페이지 사용처** 및 새로운 예외 여부. 문서에만 존재하고 코드에 없는 부분은 미구현이라고 명시.
5. **첫 시선과 행동:** 첫 화면에서 경쟁하지 않는 **주목 그룹 하나**를 정하고, 필요한 주행동 한 개(조회 화면에서는 0개 가능)와 보조 행동의 위치·강조 이유.
6. **근거와 한계:** 시안/실제 데이터/가정 구분, 실제 렌더·동작 결과 및 아직 검증하지 않은 것.

### 실제 페이지 제작의 컴포넌트 출처/시각 위계 게이트

새 화면에서 컴포넌트가 '비슷하게 생겼다'는 설명으로 임의 구현되는 것을 막기 위한 **기존 항목 4·5의 검수 기준**이다. 새 API나 생성 런타임이 아니다.

| 화면의 요소 | 먼저 선택할 실제 정본 | 웹에서 재사용할 구현 | 실패 예시 |
|---|---|---|---|
| Page Header/Back/Search | S-PAGE / NAV-TOP / C-ICON | `seed-page-shell`, `seed-top-nav`, 기존 Icon Action | 화면마다 크기·서체가 다른 헤더 |
| 보유 캐시/아이템 가격 | C-CREDIT + 필요한 C-SURFACE | 원본 `cash-coin-single.png`을 사용하는 `seed-credit` + 선택적 `seed-surface` 패널 | '캐시' 라벨과 숫자만 쓴 가짜 재화 표시, 별도 Emoji/SVG 코인 |
| 아이템 종류 필터 | C-SELECTION Filter Chip | `seed-filter-chip[aria-pressed]`와 실제 결과 목록 | 필터 그룹 안에 '보상 모아보기' 같은 다른 페이지 이동을 끼워 넣음 |
| 아이템 B | P-HIERARCHY S06 + C-IMAGE/C-TEXT + 필요한 C-CREDIT | **단일 바깥 부모** 안에 `seed-media` + 자연 높이 정보·가격 | 이미지 카드와 정보 카드 분리, 가격/이름 누락 |
| 섹션 제목 옆 이동 | P-PAGE-COMPOSE S04 + C-ACTION | 일반 링크 또는 무테 `ghost` | 별도 요구 없는 Outline/Solid/Pill 버튼 |
| 제목·캡션·강조 | F-TYPE + C-TEXT + P-HIERARCHY | `seed-text[data-text-role][data-text-style]` | 영문 overline과 Hero를 각 섹션마다 반복해 정보보다 글자가 주인공이 됨 |

**검증 순서:** 화면 요소의 목적과 동작 → 표의 기존 정본 ID → **해당 정본의 실제 CSS/함수 존재 여부** → 실 마크업 사용처 → 실제 선택/데이터/비주얼 결과. 실제 구현 클래스가 없으면 페이지별 임의 스타일로 덮지 말고 **해당 기존 정본의 공통 구현**이 필요한지 확인한다. 없는 컴포넌트/토큰을 임의로 출처가 있는 것처럼 기록하지 않는다. 초기 시연도 같은 기준이다.

**타이포 과잉 차단:** 첫 화면의 주목은 **대표 이미지·한 핵심 문구·대표 수치 중 목적상 우선하는 하나의 그룹**에 집중한다. `S04`의 '1줄형/큰형/트렌디형'은 선택 가능한 **대안**이며 같은 화면 모든 섹션에 중복 도입할 **필수 세트가 아니다**. 화면명, 영문 장식 소제목, 큰 소개 카피, 배너 제목, 상품 목록 제목이 각각 독립 Hero가 되면 **문구 추가/폰트 크기 조정 이전에 중복 정보 그룹부터 제거**한다. 필요할 때만 Section 한 단계와 짧은 Support를 사용한다. 이미 큰 이미지/배너에 글자가 있으면 인접 DOM 제목을 다시 확대·중복하지 않는다. 어떤 문구를 없앴고 무엇이 주인공인지 시각 검수에 기록한다.

**페이지 내 필터의 기본 선택:** 화면 안에서 **같은 결과 목록의 카테고리·속성·상태·추천 조건**을 바꾸는 필터라면 기존 [C-SELECTION Filter Chip](../components/selection-controls.md)을 **우선 권장**한다. 필터가 없는 화면에 억지로 추가하지 않고, 화면/목적지 전환은 Tabs·Navigation, 동일 데이터의 보기 방식 변경은 Segmented 등 원래 의미에 맞는 컨트롤을 유지한다. 예컨대 `보관함`은 단순 '보유 여부' 필터인지 별도의 보관함 화면인지 먼저 판단한다. 필터 조건과 결과를 실제로 연결하고, **필터 아래 같은 결과를 큰 타이틀로 다시 소개하지 않는다.**

**U10 · 필터 다음 콘텐츠 위계:** `C-SELECTION Filter Chip`이 한 목록/아이템 모음의 조건을 결정한다면 **필터 바로 아래에는 같은 결과 콘텐츠**가 이어지는 구성을 먼저 검토한다. `필터 → 결과 목록` 사이에 **같은 결과를 소개하는 영문 overline·큰 제목·다시 부제**를 중복 삽입하는 것은 비권장이다. 이미 필터 위에서 목록 목적을 명확히 알려줬다면 아래에서 타이틀을 다시 시작하지 않는다. 필요하면 짧은 결과 수, 상태, 정렬만 가벼운 보조 정보로 배치한다. 단, 필터가 영향을 주지 않는 **실제로 독립 섹션**은 다른 목적·새로운 정보 경계가 분명할 때 별도 타이틀을 가질 수 있다. 이 판단은 `S04`의 1줄/큰/트렌디형 선택 사례를 삭제하거나 모든 필터 다음 제목을 절대 금지하는 규칙이 아니다.

**인수 실패:** 미등록/미구현 외형을 'SEED 컴포넌트'라고 보고, 공유 구현이 있는데도 페이지 CSS에서 같은 모양을 재작성하거나, 보유 캐시의 원본 코인을 대체하거나, 여러 강조 헤드라인 때문에 제품/가격/탐색이 첫 화면에서 밀리면 **레이아웃 제작 성공과 관계없이 SEED 적용 실패**다. 실제 브라우저 검수 없이 완료로 표시하지 않는다.

**예시 기록 (화면 확정안 아님):** '클랜 멤버 기여도는 수치를 비교하므로 세로 배치 + List. 동등한 수치 기준선과 약한 Divider를 택함. 웹툰의 이미지 중심 인기 작품 목록은 순차 발견이므로 Rail + Image Frame. 둘 다 랭킹이지만 동일 Layout 강제하지 않음.'

## 8. 실패를 판단하고 돌아갈 위치

| 증상 | 먼저 확인할 판단 | 수정 대상 |
|---|---|---|
| 이벤트 상자가 구성원 활동을 밀어냄 | 페이지 주연·섹션 책임·면적 배분 | Page/섹션 지도; 높이만 임시 축소 금지 |
| 이미지+작은 이름뿐이라 아이템을 해석 못함 | 정보 슬롯·상태·가격의 맥락 | 객체 조합과 C-IMAGE/C-CREDIT; Grid 자체 수정 아님 |
| 모든 화면이 같은 카드 목록처럼 보임 | 데이터의 비교/탐색/표현 목적과 Surface 과용 | Layout 선택 + C-SURFACE |
| 같은 버튼이 페이지마다 모양·크기가 바뀜 | 기존 컴포넌트 Variant 재사용 여부 | C-ACTION·공통 스타일, Layout 별도 추가 금지 |
| 배지 위치가 화면마다 어긋남 | Image Frame/컴포넌트에 이미 Anchor가 있는가 | 기존 Component 슬롯, 별도 Layer 생성 금지 |
| 상세 화면 버튼이 하단바·키보드에 가림 | Shell의 fixed 영역·inset 소유권 | S-PAGE; 지역 padding 누적 금지 |
| 브라우저 렌더는 되지만 디자인 목적이 전달 안 됨 | 첫 시선·정보 위계·원본 아트·행동 관계 | 해당 Page/Pattern 선택. 테스트 수만 늘리지 않음 |

## 9. 재사용 표준 스타일과 페이지 전용 표현

디자인 SEED의 수치를 새 페이지의 CSS/Compose에 하나하나 복사하지 않는다. [표준 스타일 적용 체계](../implementation/shared-style-contract.md)에 정의된 **기존 공통 클래스·Theme·컴포넌트 진입점**을 사용한다. 페이지는 목적에 따른 Section의 순서·Layout의 비율·열 수·콘텐츠만 소유한다.

- 같은 버튼·아이콘·이미지·타이포는 같은 공통 구현을 참조하고, 허용된 Variant/State로 구분한다.
- 예외를 위해 페이지 CSS가 기존 컴포넌트의 기본 패딩/Radius/색을 덮지 않는다. 책임이 공통 컴포넌트인지 배치인지 먼저 판단한다.
- 문서에 표준 API가 적혀 있어도 실제 CSS 또는 Compose에 구현이 없으면 **미구현**으로 기록한다. 구현을 확인하기 전 '자동 적용'이라고 보고하지 않는다.

## 9. 검토의 경계

- 이번 문서화는 **범용 레이아웃과 페이지 선택 규칙의 설계안**이다. 새 UI 코드·페이지 시연·이동 동작·네이티브·접근성 실증은 다루지 않는다.
- [VALIDATION](../VALIDATION.md)의 실행/규격/객체·조합/페이지 목적/행동·회귀 다섯 축은 유지한다. 문서 간 경로가 맞다고 디자인 품질이 입증된 것은 아니다.
- 최종 홈/클랜/마이/상점의 콘텐츠 순서·면적 및 아트 강도는 실제 화면에서 판단한다. 해당 미결은 [OPEN](../../../OPEN.md)에 남아 있다.
